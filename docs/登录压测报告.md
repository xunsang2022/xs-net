# 登录（认证）压测报告

> 压测脚本：`game-client/src/main/java/com/game/client/LoginLoadTest.java`
> 文档生成时间：2026-08-27（更新：登录链路已打通，覆盖完整 CS_Login→SC_Login 闭环）
> 目标：模拟 **1000 玩家同时登录**，评估网关在「并发连接 + JWT 认证 + 进服登录」上的压力。

---

## 1. 背景与目的

网关「登录」能力包含两段闭环，本脚本覆盖完整链路：

- **连接 + 认证**：通过客户端本地按网关相同密钥/声明（`sub=playerId`, `cid=channelId`）签发 JWT，
  避免压测时依赖 Login HTTP 服务，把压力集中在网关认证链路。
- **进服登录**：认证通过后发送 `CS_Login`（rpc 1000），网关将其转换为内部 `PlayerEnterCommand`
  路由到 Logic `PlayerActor`，进服/落库完成后经 S2C shard 回推 `SC_Login`（rpc 1002）。
  收到 `SC_Login` 即判定登录成功（而非仅保持连接）。

- 用固定线程池限制并发，模拟「同一时刻最多 `concurrency` 个玩家在途」的持续并发登录。
- 统计登录成功率、时延分位（avg/p50/p95/p99/max）与吞吐。

## 2. 前置条件

## 4. 认证成功判定（按网关真实协议）

| 协议 | 流程 | 成功判定 |
|---|---|---|
| **TCP** | 连上后首帧发 `JWT(UTF-8)`；认证通过网关保持连接，失败立即 `close` | 验证窗口内连接保持打开（读到 EOF 即失败） |
| **UDP** | 发 `HELLO(JWT)`，网关校验通过回 `ACK` | 收到 `ACK` |

> TCP 无正向 ACK，故用「验证窗口内连接未关闭」判定成功；该窗口会抬升单次时延（约等于 `verify-ms`），属 TCP 判定方式的固有特点。

## 6. 结论与发现

### 6.1 TCP 并发上限受连接队列（backlog）限制 —— 已修复

- 网关 Netty `SO_BACKLOG` 原为硬编码 128（见 `NettyServer.start()`），并发 200 > 128 时 accept 队列溢出 → 客户端 `Connection refused`。
- **修复**：新增 `game.netty.backlog` 配置（默认 1024），`NettyServer` 改用 `config.getBacklog()`。
- 修复后并发 200 达到 **1000/1000** 成功。生产环境按预期并发调大 `SO_BACKLOG` 即可。

### 6.2 UDP 单 I/O 线程为吞吐瓶颈 —— 已修复

- 原 UDP 服务器仅 1 个 I/O 线程（`new NioEventLoopGroup(1)`），且解码/验签/建会话/回 ACK 均在单个 `NioDatagramChannel` 绑定的 event loop 上串行执行。
- 单纯增大 event loop 线程数无效——单 channel 只绑定一个 loop。
- **修复**：新增 `game.udp.business-threads` 业务线程池（默认 2 * CPU），`UdpAuthHandler` 收到包后立即拷贝字节并提交线程池并行处理；同一会话内以 `synchronized(session)` 保证可靠层有序，不同会话并行；每会话认证日志降为 debug 减少热路径 I/O。
- 修复后并发 1000 达到 **1000/1000**、吞吐 **2415.5/s**（修复前 650/1000、21.5/s）。

### 6.3 已修复：打通 `CS_Login → PlayerActor` 完整登录闭环

- **原缺陷**：网关 `AuthHandler.handleGameMessage` / `UdpAuthHandler` 对所有 C2S 消息无条件强转为 `PlayerMessage`：
  ```java
  AkkaKit.tell(PlayerMessage.class, (PlayerMessage) actionMessage, playerId);
  ```
  `CS_Login`（rpc 1000，`com.game.message.c2s.LoginRequest`）是 `Rpc.Kind.MESSAGE`，未实现 `PlayerMessage`，
  发送会抛 `ClassCastException` 并断连；`CS_Login → PlayerActor` 登录链路此前未接通。
- **修复**：
  1. `AuthHandler` / `UdpAuthHandler` 识别 `LoginRequest`，转换为内部 `PlayerEnterCommand` 再路由到 `PlayerActor`，
     避免对未实现 `PlayerMessage` 的消息强转（[AuthHandler.java](file:///e:/project/xs-net/game-server/game-node-gateway/src/main/java/com/game/gateway/netty/AuthHandler.java#L139-L145)）。
  2. `LoginResponse` 实现 `S2C` 接口；RPC 生成器为纯下行 S2C 消息分配 `roleClass = S2C`，
     使 Logic 节点创建 S2C shard proxy（日志可见 `Starting Shard Region Proxy [S2C]`），下行可路由回网关回客户端。
  3. `PlayerActor` 进服/落库完成后 `sendRpc(S2C.class, LoginResponse, channelId)` 回推 `SC_Login`（rpc 1002）。
- 压测脚本同步升级为「发送 `CS_Login` 并等待 `SC_Login`」判定登录成功，覆盖完整闭环。
- **额外修复（落库）**：`DBSyncEngine` 落库时此前 `destroyState` 仅提交脏字段导致 `last_login_at` 为 NULL，
  违反 NOT NULL 约束；改为提交完整 state hash（`state.toHash()`），确保全量 NOT NULL 列恒有值。

## 6.5 调优（最强水平）

针对「新玩家冷登录」（每次登录都需 DB `UPSERT...RETURNING` 建行）热路径做了如下调优，全部 1000/1000 成功：

### 已保留（有效）

| 优化 | 说明 |
|---|---|
| **DB 建行合并为单次往返** | `DBSyncEngine.loadOrCreate` 由「INSERT ON CONFLICT + SELECT」两次 DB 往返合并为一次 `UPSERT ... RETURNING`，新玩家冷登录省一半 DB 时延 |
| **移除登录热路径冗余 Redis 写** | `PlayerActor.finishLoad` 中 `create` 已全量写 Redis，删除其后的冗余 `flushDirty`，登录路径少一次 Redis 往返 |
| **DB 连接池调大** | `game.db.max-pool-size` 20→50，HikariCP 并发取数不再成为瓶颈 |
| **Redis 连接池调大** | Lettuce 池 `maxTotal/maxIdle` 8→32、`minIdle` 0→4，登录热路径 Redis 并发取数充足 |
| **网关线程显式化** | TCP `worker/business` 64/64、UDP `worker/business` 32/64，充分利用 32 核 CPU |
| **分片实体专用 Dispatcher** | `xs-entity-dispatcher`（`fixed-pool-size=256`、`throughput=1`），PlayerMessage / S2C 通道实体统一使用大容量线程池；默认 32 线程 fork-join 在 TCP 并发 200 场景成瓶颈，扩大实体并发能力。大小可通过环境变量 `XS_ENTITY_POOL` / `XS_ENTITY_THROUGHPUT` 覆盖 |

### 已尝试并回退（无效/负收益）

| 尝试 | 结果 | 结论 |
|---|---|---|
| **专用 DB 加载线程池**（`game.db.load-threads`） | 吞吐未提升 | 默认 `CompletableFuture.supplyAsync` 使用的公共 ForkJoinPool 并行度≈CPU−1=31，与 32 线程专用池等价，无额外收益，回退 |
| **Dispatcher 仅用于 logic 实体**（S2C 通道保持默认） | UDP 显著回落（~830/s） | S2C 通道实体在 UDP 1000 并发下同样需要专用大线程池，移出后与网关默认 dispatcher 争用线程，回退为全部实体统一使用 |

> 实现注意：`Entity<?>` 单参数通配符与 Akka typed `Entity<M,E>` 双类型参数冲突，运行期抛
> `Incorrect number of arguments for type Entity<M,E>` 导致 shard region 初始化失败；
> 需用 raw 类型局部变量再链式 `withEntityProps`。

### 最终结果（含 6.5 保留项，dispatcher=256/1）

- 冷登录路径吞吐受 DB 建行 + Redis 落库 + S2C 回包整体链路决定，本机多次采样取均值：
  - **TCP**（并发 200）：基线 ~527 登录/s → 调优后 **~850 登录/s**（+60%，样本 757–961）
  - **UDP**（并发 1000）：基线 ~1196 登录/s → 调优后 **~990 登录/s**（−17%，样本 897–1150）
- UDP 由于无 TCP `verify-ms` 判定窗口且可并行，绝对吞吐仍高于 TCP；dispatcher 扩大实体并发后 TCP 收益显著。
- 单次 DB `UPSERT` 裸测（DBBench）可达 ~5000/s，应用侧冷登录吞吐受「Redis 读+DB 建行+Redis 落库+S2C 回包」整链编排限制，DB 本身不是瓶颈。

## 7. 输出解读

- **认证成功 / 失败**：网关在并发压力下能否稳定放行连接并完成 JWT 校验。
- **吞吐(登录/s)**：单位时间完成的认证数（受 `concurrency` 与 TCP `verify-ms` 窗口制约）。
- **时延分位**：认证完成的端到端耗时，p99 反映尾部压力。

> 以上结果为本机单机、三节点集群、未调优参数的基线值；生产环境需结合部署拓扑、网络与硬件重新压测。
