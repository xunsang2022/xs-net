# 登录压测报告

> 压测入口：`xs-net-sdk-unity/LoadTest/XsNet.LoadTest.csproj`
>
> 最近执行：2026-08-28
>
> 测试范围：TCP/UDP 的 `CS_Login → Gateway → PlayerActor → SC_Login` 完整登录闭环。

## 1. 测试目的

验证 Gateway 在 JWT 认证、协议解码、玩家登录路由和 S2C 回包全部参与时的登录正确性与初始性能表现。成功标准不是连接建立或认证通过，而是客户端收到 `SC_Login`（rpc 1002）且返回码为 `0`。

压测工程直接复用 Unity Runtime 的 TCP、UDP、可靠 UDP、Protobuf 编解码和消息分发逻辑；控制台程序仅负责虚拟玩家并发、JWT 生成和统计。

## 2. 环境与协议

- 本机 Windows 环境；Gateway、Logic、Login 均为本地 Java 进程。
- Gateway TCP：`127.0.0.1:8082`。
- Gateway UDP：`127.0.0.1:2002`。
- JWT：HS256，声明包含 `sub`（玩家 ID）与 `cid`（认证通道 ID）。
- TCP：首帧发送 JWT，后续发送长度前缀加 `NetMessage`。
- UDP：先发送 `HELLO(JWT)`，收到 `ACK` 后通过可靠 UDP 发送游戏消息。

## 3. 执行方式

先构建压测工程：

```powershell
dotnet build xs-net-sdk-unity/LoadTest/XsNet.LoadTest.csproj
```

TCP 示例：

```powershell
dotnet run --project xs-net-sdk-unity/LoadTest/XsNet.LoadTest.csproj --no-build -- --host 127.0.0.1 --protocol tcp --port 8082 --count 500 --concurrency 100 --timeout-ms 10000 --player-start 60001 --secret $env:JWT_SECRET
```

UDP 示例：

```powershell
dotnet run --project xs-net-sdk-unity/LoadTest/XsNet.LoadTest.csproj --no-build -- --host 127.0.0.1 --protocol udp --port 2002 --count 100 --concurrency 25 --timeout-ms 10000 --player-start 50001 --secret $env:JWT_SECRET
```

`--secret` 必须与 Gateway 的 JWT 密钥一致；不得将生产密钥写入命令历史、文档或版本库。

## 5. 本轮发现与修复

### 5.1 TCP 下行回包路由

压测端此前在 JWT 的 `cid` 与 `CS_Login.SessionId` 中使用了不同值。Gateway 认证阶段按 `cid` 注册连接，但登录链路把客户端请求中的 `sessionId` 用作 S2C 路由键，导致 `SC_Login` 无法找到连接并被丢弃。

压测端已改为让二者使用同一个 `channelId`，TCP 完整登录闭环已验证通过。

### 5.2 Unity UDP Runtime 未实际发包

`UdpConnection` 调用 `UdpClient.Send` 时将发送长度传为 `0`，导致 HELLO、DATA、ACK、重传和心跳数据报均为空。已改为传递实际数据报长度：

```csharp
client.Send(hello, hello.Length);
_client.Send(datagram, datagram.Length);
```

修复后已通过 UDP 单用户和 100 玩家并发登录闭环验证。

### 5.3 Pekko Artery 空闲唤醒时延（低并发低延迟主因之一）

低并发（c=1~5）下峰值时延曾达数十毫秒级，主要来自 embedded 媒体驱动的空闲休眠唤醒。默认 `idle-cpu-level=8` 在空闲轮询较休眠更久、唤醒更慢。

已在 Gateway 与 Logic 的 `application.conf` 增加 `advanced.embedded-media-driver.idle-cpu-level = 3`（可用 `PEKKO_IDLE_CPU_LEVEL` 覆盖），让空闲时保持高频轮询，以少量 CPU 换毫秒级时延。配合埋点确认后，warm 态 c=1 登录 p50 已稳定降至 ~15 ms。

关联文件：`game-server/game-node-gateway/src/main/resources/application.conf`、`game-server/game-node-modules/src/main/resources/application.conf`。

## 6. 结论与限制

- 本轮 TCP 500/100 与 UDP 100/25 均达到 100% 登录成功，验证 Unity Runtime 复用的 .NET 压测端可覆盖真实 TCP/UDP 登录协议与完整 S2C 回包。
- TCP 和 UDP 使用的玩家数、并发数不同，不能据此直接得出两种协议的吞吐优劣结论。
- 当前结果仅是本机少量样本，不代表稳定极限吞吐。后续应在同规模、多轮重复的隔离环境中，同时采集 Gateway、Logic、Redis、PostgreSQL 的 CPU、GC、连接池和错误指标。
- 服务端仍不应信任客户端 `CS_Login.sessionId` 作为下行通道路由键。应由 TCP/UDP 认证处理器把可信的 JWT `cid` 显式传入路由器，并忽略或覆盖客户端传入的 sessionId。
- 多 Gateway 节点时，进程内 `ChannelRegistry` 不能跨节点寻址；需要明确连接归属与跨 Gateway 的下行路由方案。
