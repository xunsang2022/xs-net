# xs-net 产品形态与生态路线规划

> 本文档规划 xs-net 从「内部代码库」走向何种「产品形态」及其对应的生态建设路线。
> 参照竞品：ioGame / skynet / ET；技术基础见 `ARCHITECTURE.md`。
> 更新日期：2026-08-28
>
> 全文明确区分 **现状（事实）** 与 **建议（规划判断）**，不编造数据与事实。

---

## 0. 背景与约束

### 0.1 技术栈现状（事实）

依据 `ARCHITECTURE.md`，xs-net 的核心技术栈为：

| 技术 | 版本 | 说明 |
|---|---|---|
| Java | 21 | 开发语言 |
| Spring Boot | 4.0.0 | Gateway / Login Web 框架 |
| Akka | 2.8.5 | Cluster + Sharding，Artery/Aeron UDP 传输（**BSL 授权**） |
| Netty | 4.1.115 | Gateway TCP 长连接 |
| Protobuf | 3.25.5 | `NetMessage` 信封及序列化 |
| Redis | - | Logic 运行时状态与 Streams |
| PostgreSQL | - | 最终持久化 |
| JWT (jjwt) | 0.12.6 | 身份认证 |
| Micrometer | 1.16.0 | 指标 |

架构要点：Gateway（无状态，连接/认证/路由/写回）— Login（JWT）— Logic（非 Spring Boot 的普通 Java + Akka Cluster Sharding 承载 `PlayerActor`/`DBSyncEngine`/`LogConsumer`）；协议为 `4 字节大端长度前缀 + NetMessage(protobuf)`；有 RPC 代码生成 Maven 插件（`xs-net-rpc-maven-plugin`）与 SDK。

### 0.2 现状盘点（事实）

- 仓库已具备框架级划分：`xs-net-core`（Akka 封装）、`xs-net-message`（协议契约与编解码）、`xs-net-rpc-maven-plugin`（RPC/SDK 生成插件）、`xs-net-sdk`、`xs-net-tools`，以及 `game-server/*` 服务端模块。
- 已有内部架构/协议/压测文档（`docs/`），但**尚无对外文档站、示例游戏、贡献指南、许可证声明**等对外生态。
- 运行依赖 Akka（BSL），这是对外发布与商业化前必须厘清的许可风险点（详见第 5 节）。

### 0.3 本文目标（建议）

明确三种可选产品定位（纯内部底座 / 开源自研 / 商业化服务）的利弊与取舍，确定各自所需的生态工程，并据此给出分阶段路线图与可度量指标。

## 1. 竞品参照：ioGame / skynet / ET

> 以下为公开可得的一般性认识（现状/事实层面），用于参照生态与定位，不作为 xs-net 的承诺数据。

### 1.1 概览

| 维度 | ioGame | skynet | ET（ET Framework） |
|---|---|---|---|
| 语言 | Java | C + Lua | C# |
| 定位 | Actor 化轻量游戏服务器框架 | 分布式游戏服务框架（单进程多服务） | 服务端 + 客户端一体（双端） |
| 组织模型 | 事件驱动 + 逻辑多线程 | 消息驱动 + 服务（service） | ECS / 组件化 |
| 生态 | 文档站 + 示例，国内社区活跃 | 中文文档/社区成熟，历经多年生产验证 | 社区项目，Unity 场景常见 |
| 许可 | Apache-2.0 等开源许可 | MIT 兼容的自定义开源许可 | 开源许可 |

### 1.2 对 xs-net 的参照意义（建议）

- **ioGame**：印证「开源 + 文档站 + 可运行示例」是 Java 游戏框架获取采用者的最低门槛；心智是轻量、开箱即用。
- **skynet**：印证「框架经过真实游戏生产验证 + 长期维护 + 活跃社区」是生态粘性的核心，启动更早者占优。
- **ET**：印证「双端一体」可作为差异化方向，但工程复杂度与维护成本显著更高。

xs-net 的技术选型（Java 21 + Akka Cluster + Protobuf + 代码生成器）与 ioGame 用户群高度重叠，属直接竞争面；与 skynet/ET 语言栈不同，主要竞争「架构选型心智」。

## 2. 三种产品定位：利弊与取舍

### 2.1 定位 A：纯内部底座（In-house Foundation）

**讲述（现状）：** 保持现状，仅服务于自研游戏项目，代码不对外，无对外生态投入。

| 维度 | 内容 |
|---|---|
| 利 | 无对外承诺压力；可随时重构；无需处理文档/社区/许可对外问题；开发节奏由内部需求驱动 |
| 弊 | 无外部反馈，演进取样有限；Akka BSL 的许可风险仍需自行消化（付费或换 Pekko）；知识/技能沉淀不产生行业影响力；孤岛化，招人与团队复用成本高 |
| 关键决策 | 仍须决定 Akka BSL 的企业级去向（购买 / 满足免费条件 / 迁移 Pekko），只是不涉及对外公开 |

**取舍：** 若团队只做 1~2 个自用游戏、追求最小维护成本，A 优先。

### 2.2 定位 B：开源自研（Open Source First）

**讲述（建议）：** 以开源许可对外发布，建立文档站、示例、贡献者社区，**不直接售卖软件授权**，以品牌/采用者/人才/生态反哺业务。

| 维度 | 内容 |
|---|---|
| 利 | 建立行业信任与采用者基数；吸引社区贡献与人才；为后续商业化铺路；获得外部压力促进行工程质量 |
| 弊 | 需持续投入文档维护/Issue 治理/版本发布；代码公开暴露架构细节；无直接收入；社区冷启动慢、维护者精力被稀释 |
| 关键瓶颈 | **Akka BSL 无法作为 Apache-2.0 对外开源的基础依赖透传**（外部采用者拿到的是 BSL 依赖，会显著降低采用意愿）→ 建议对外开源前先迁移到 Apache Pekko（见第 5 节）。协议对外许可建议 Apache-2.0 或 MIT（自身代码），与 Pekko 兼容 |

**取舍：** 若要「被采用」，B 是必经路径；但必须同时交付「文档站 + 可运行示例 + 迁移备忘录」，否则 Stars/采用者不会自然增长。

### 2.3 定位 C：商业化服务（Commercial Service）

**讲述（建议）：** 在 B 开源基础上，面向企业提供增值服务，如：私有化部署交付、定制开发、性能调优、技术咨询、企业级支持 SLA。

| 维度 | 内容 |
|---|---|
| 利 | 直接收入；以服务反哺框架演进；企业客户驱动稳定性与安全投入 |
| 弊 | 需成立销售/售后/合同/合规职能；开源与闭源边界模糊易引发社区不满；与 B 的重心冲突，需明确「开源版 vs 企业版」差异 |
| 关键瓶颈 | 合规复杂：依赖 Akka（BSL，商用生产需购买 Lightbend 许可）、引入 Apache Pekko 可大幅简化对客户交付的许可链条；需提供开源版合规外带（依赖清单/license audit） |

**取舍：** C 依赖 B 的先发积累（没有采用者基数，商业化无抓手）；且 BSL 链条处理不到位会放大法务风险。

### 2.4 定位对比与选择建议

| 评估项 | A 纯内部 | B 开源自研 | C 商业化服务 |
|---|---|---|---|
| 工程投入 | 低 | 中–高 | 高 |
| 许可风险自担 | 高（不公开） | 中（公开即暴露） | 高（商用交付易触雷） |
| 行业影响力 | 无 | 主要来源 | 随服务扩大 |
| 收入 | 无 | 无/间接 | 直接 |
| 冷启动难度 | - | 高 | 极高（依赖 B） |

> **建议（分阶段）：** 现阶段以 **A → B** 为稳妥主线——先内部固化并处理 Akka→Pekko 迁移，再择机对外开源建立采用者与文档。**C 作为远期选项**，视 B 阶段采用者规模（见 6.2 指标）再决定是否启动商业服务团队。不建议「跳过 B 直接 C」。

## 3. 生态工程清单

> 依据定位不同裁剪；以下给出按需的生态工程清单（建议）。A 定位可全部豁免，B 至少覆盖 3.1–3.4，C 另加 3.5。

### 3.1 文档站（现状缺失 → 建议建设）

- 现状：仅有仓库内 `docs/`（架构、协议、压测），无对外站点。
- 建议：
  - 站内结构：快速上手 → 概念与架构 → 协议与 RPC 生成器 → 部署（Gateway/Login/Logic/Redis/PG）→ 常见问题 → 版本发布说明（CHANGELOG）。
  - 托管方案：静态文档站（如 MkDocs Material / Docusaurus）挂到仓库 `docs/site` 目录并配 CI 构建发布；保留 markdown 便于协作与版本化。
  - 引入「Get Started in 10 分钟」一节：`git clone → mvnw → docker-compose up → SDK 示例` 跑通最小链路。

### 3.2 示例游戏（现状缺失 → 建议建设）

- 现状：原 `game-client` 联调端已移除，压测/联调由 `xs-net-sdk` 承担；非可玩示例。
- 建议：
  - 交付一个**最小但完整的示例**（如单场景房间游戏：登录 → 匹配/进房 → Actor 内状态更新 → 批量落库），覆盖「上行 RPC → PlayerActor → Redis/PG 持久化 → S2C 写回」全链路，作为所有新人的模板。
  - 明确示例与框架的边界：示例放在独立示例仓库或 `examples/` 目录，保持可独立 `git clone` 复现。

### 3.3 贡献指南（现状缺失 → 建议建设）

- 现状：无 CONTRIBUTING/路线说明。
- 建议：
  - `CONTRIBUTING.md`：分支规范、提交信息规范（Conventional Commits 可选）、测试要求（行为变更需补针对性测试，与仓库 AGENTS.md 约定一致）。
  - `ROADMAP.md`：公开开发方向与优先级，降低贡献者门槛。
  - PR 模板与 Issue 模板，规范社区提交。

### 3.4 许可合规（现状待处理）：

- 现状事实：运行依赖 Akka 2.8.5（BSL 授权，商用生产需 Lightbend 许可或满足免费条件），详见第 5 节。
- 建议：任何「对外发布（B/C）」动作前，先完成依赖许可审计并与 Apache Pekko 评估后定生存续方案。

### 3.5 商业化服务支撑（仅 C 定位，建议，远期）

- 企业交付包：部署清单 + 配置文件模板 + 运维手册 + 监控（Micrometer）接入指引。
- 商务配套：开源版/企业版区别说明、SLA 模板、依赖许可外带（license audit 清单）。

## 4. Akka BSL 商用许可约束与 Apache Pekko 替代

### 4.1 Akka 许可现状（事实）

- Akka 自 2022-09（2.7 起）改用 **Business Source License（BSL）v1.1**（由 MariaDB 推广的「源代码可得」许可，非 OSI 开源许可）。
- BSL 允许**开发/非生产环境的自由使用**；**生产环境使用需从 Lightbend 获取商业许可**。
- Lightbend 提供**免费生产许可**给：开源项目、教育/学术界、年收入低于 $25M 的初创公司。
- **License Key 引入**：自 2.9.6、2.8.7、2.7.1 及之后版本起，生产环境需要 license key；每个版本在 **Change Date（3 年）后**自动转为 Apache-2.0。例如 Akka 2.8.0 的 Change Date 为 2026-03-16（已到 Apache-2.0 窗口）；**各补丁版本 Change Date 独立，2.8.5 的具体 Change Date 需以其仓库该版本 LICENSE 为准核实**（本仓库当前无该核实的显式记录，属待办）。

### 4.2 对 xs-net 的约束（分析，建议核对）

- xs-net 当前锁定 Akka 2.8.5。
  - 若进入**对外开源（B）**：下游采用者拿到的是一个以 BSL 依赖为底座的框架，难以被普遍接受为「Apache-2.0 干净可商用的游戏框架」，显著压制采用意愿。
  - 若进入**商业化交付（C）**：需为每份生产交付处理 Lightbend 商业许可，或确认满足免费条件，法务与商务复杂度上升。
  - 若继续**内部用（A）**：也需在「购买许可 / 满足免费条件 / 迁移 Pekko」间作出企业决策，仅是不对外展示。

### 4.3 Apache Pekko 替代（建议的迁移去向）

- **Apache Pekko** 是 Akka 更换 BSL 后，由 ASF 维护的 **Apache-2.0** 兼容分叉（2024 年从 Apache 孵化器毕业为顶级项目），沿用 Akka actor/cluster/sharding 生态。
- 迁移要点（建议，需在迁移验证中核对）：
  - Java 包名：`akka.*` → `org.apache.pekko.*`；配置前缀 `akka.` → `pekko.`。
  - 基础出入为「批量替换 + 排除个别模块（如 akka-management / akka-http 类能力在 Pekko 生态中的对应物）」。
  - 本项目使用 **Artery/Aeron UDP** 传输，需核对 Pekko 对应配置项与兼容性后再切换。
- 迁移收益（建议）：对外开源/商业化时拿到干净的 Apache-2.0 依赖链，避免 BSL 成为采用与交付障碍。
- 迁移成本（建议）：涉及 `xs-net-core` 的 Akka 封装、配置与依赖坐标统一调整，建议在独立分支隔离验证，跑通现有压测/联调后再合入。

> **建议结论：** 若走 B/C 定位，将 **Akka→Apache Pekko** 迁移纳入路线图前置阶段；若保持 A 定位，至少完成「BSL 合规确认或迁移」以消除风险敞口。

## 5. 路线图与指标

### 5.1 分阶段路线图（建议）

| 阶段 | 周期（估算） | 关键交付物 | 对应定位 |
|---|---|---|---|
| P0 内部固化（现状） | 短期 | 架构/协议/压测文档完备；CI 与示例跑通；**完成 Akka→Pekko 迁移决策与验证** | A |
| P1 许可与工程化 | P0 后 | Pekko 迁移合并；依赖许可审计；`CONTRIBUTING.md`/Issue·PR 模板；CHANGELOG 机制 | A→B |
| P2 对外发布 | P1 后 | 开源许可声明 + LICENSE；文档站上线；最小可运行示例；Quick Start 指南 | B |
| P3 社区运营 | 持续 | `ROADMAP.md` 公开；Issue 治理；首个采用者基线；版本化发布节奏 | B |
| P4 商业化评估（远期/条件性） | 视 P3 采用者 | 企业交付包、SLA、开源/企业版划分 | B→C |

> 周期为弹性参考，非承诺；关键前置依赖：P1 的 Pekko 迁移必须在前，P2 才具备对外可接受性。

### 5.2 指标体系（建议，基于事实口径，不预先设定虚高目标）

> 以下为「提议采用的度量方式」，具体目标值应在立项时依据团队资源另行设定，本文不做编造性承诺。

| 指标 | 口径 / 衡量方式 | 关联阶段 |
|---|---|---|
| Stars / Forks | GitHub 仓库可见度（用于发现度，非质量唯一标准） | P2–P3 |
| 采用者数 | 提交的 Issue/PR、提及、文档下载/站点访问、`game-node` 模板使用 |
| 移交文档完备度 | 以清单评分：架构/协议/部署/示例/贡献/许可/CHANGELOG 各单项齐全度 | 全体 |
| 代码生成器使用 | `xs-net-rpc-maven-plugin` 被外部使用的反馈/疑问 | P2–P3 |

事务化兜底：文档站与 README 顶部标注「当前定位与阶段」，避免使用者误解成熟度。

## 6. 风险与开放问题

- **未决：Akka 2.8.5 的确切 Change Date 核实**（本文标注为待办，需读取该版本 LICENSE 文件确认；若已近/已过 Apache-2.0 窗口，Pekko 迁移紧迫度可相应评估，但 BSL→Apache 的窗口是「版本级」退回，仍需以版本为准）。
- **未决：对外许可形态**（Apache-2.0 或 MIT）需与正则约束、示例代码共享后一致确定。
- **风险：Pekko 迁移对 Artery/Aeron、集群发现（配置）及 Spring Boot 集成的影响**未验证，属 P1 必须完成的验证项。
- **风险：社区冷启动**——选择 B 需长期承诺文档与 Issue 治理，资源不足将适得其反。
- **范围明确：本文不承诺具体时间点与具体 Stars/采用者数字**，只给出度量方式与顺序；最终落地目标应由项目负责人立项时设定。
